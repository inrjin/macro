# 다중 에이전트 교차 검토

검토일: 2026-10-21. 대상은 `Integrated-Macro-v0.5.0` 안의 0.5.8 이후 소스다. 기존 배포 앱의 실사용 성공을 의미하지 않는다. 배포 패키징 없이 소스 수정과 테스트용 컴파일을 진행했다.

## 검토 방식

총 4명이 플랫폼 입력, 실행 엔진, UI·설정 저장, 영상 판단·성능을 나눠 조사했다. 최초 재현 후 담당자가 수정하고, 다른 담당이 응답 순서·중지·불완전 화면을 반례로 넣었다. 이 과정에서 수정안 자체의 RGB·좌표 혼합과 늦은 시작 응답 문제도 발견해 다시 검토했다. 모든 가능한 오류를 소진했다는 주장은 하지 않는다.

## 확인한 문제와 조치

| 문제 | 확인 근거 | 변경 |

설정 충돌 복구의 첫 수정안은 RGB·좌표의 각 성분을 독립 병합해 지정하지 않은 색·위치를 만들 수 있었다. 재검토에서 이를 발견했으며 색상, 점, 사각형, 캡처 크기·배율은 각각 한 값으로 취급한다. 독립된 일반 옵션 변경은 보존한다. 중지 이후 늦은 성공 응답의 창 최소화 및 상태 표시 역전도 수정하고 재검토했다.

큰 영역 합성 실험의 추가 힙 할당 최대치는 72,508,032→6,447,744바이트, 5회 중앙 실행 시간은 29.544→26.173ms였다. 실제 티켓 사이트 지연이나 앱 전체 메모리 측정값은 아니다. [측정 소스와 한계](audit-round1-vision/README.md).

## 검증 기록

최종 결과는 **JavaScript 137개 + Rust 242개 = 379개 통과, 실패 0개**다. Mac arm64·x86_64 Swift 컴파일 및 호스트 ABI·합성 검사도 통과했다. 네이티브 검사에는 샌드박스 OS 서비스 경고가 있었으며 실제 권한·입력 성공의 근거로 사용하지 않았다.

최종 소스 96개 지문은 동결 이후 변경되지 않았고, 기존 앱 실행 파일·ZIP과 루트 AGENTS.md의 해시도 기존 값과 일치했다. [검증 결과와 소스 지문](multi-agent-audit.json), [JavaScript 로그](audit-final-js.log), [Rust 로그](audit-final-rust.log), [Mac 네이티브 로그](audit-final-native.log)에 기록했다.

- UI는 실제 `app.js`를 DOM harness에서 실행하고 IPC 응답 순서를 통제했다. 실제 Tauri 앱 실행은 아니다.
- 엔진 회귀는 실제 Rust Engine과 헬퍼·요청 큐를 사용했다. 창 검증·OS 입력 전송은 장벽이나 카운터로 대체한 검사와 분리한다.
- Mac 네이티브는 arm64·x86_64 Swift 컴파일 및 호스트 ABI·합성 이벤트·사용자 제공 9개 입력 메타데이터 재생을 검사한다. 실제 키·마우스 입력을 보내지 않는다.
- 수정 전 증거: [UI·설정](audit-round1-ui/README.md), [입력 검증 경계](audit-round1-platform/metadata.json), [프레임 전환](audit-round1-runtime/README.md).

## 남아 있는 한계

1. 배포 앱의 실제 물리 입력→첫 입력 기준색 저장→캡챠 닫힘→좌석 클릭은 아직 실기 확인하지 않았다. [앞선 키보드 원인 분석](keyboard-repair-review.md)의 사용자 로그 재생 결과와 구분한다.
2. 캡챠 판단은 첫 입력 시 저장한 왼쪽 아래 배경색과 이후 색 변화를 비교하는 휴리스틱이다. 그 부분이 충분히 변하지 않으면 놓칠 수 있고, 관련 없는 큰 화면 변화도 구분하지 못한다. F9 수동 진행을 유지했다.
3. Mac 프레임 시각은 ScreenCaptureKit 콜백 도착 시각이다. OS 안에서 지연된 옛 이미지가 입력 후 도착하는 경우까지 배제하거나 사이트의 렌더링 완료를 증명하지 못한다.
4. 마지막 취소 검사와 OS 전송 사이의 짧은 경쟁은 남는다. 이미 보낸 입력은 되돌릴 수 없으며, down을 보낸 경우 대응하는 up은 보낸다. OS 전송 성공은 서버의 좌석 선점 성공이 아니다.
5. 화면 변화 감지는 알림 문구를 읽지 않는다. 일반 중앙 화면 변경도 알림으로 오인할 수 있다. 불투명도 검사는 64×48 표본 검사이며 전체 픽셀의 유효성을 보장하지 않는다.
6. 새 20초 응답 제한 취소는 UI 시작 요청에 적용한다. 모든 종류의 IPC 작업을 강제 중단하는 일반 취소 체계는 아니다. 블로킹 OS 호출 자체를 강제로 종료하지 않는다.
7. Windows 실제 빌드·실행, 실사이트별 화면 차이, 실제 예약 시각과 서버 좌석 결과는 미검증이다. 이번 테스트로 이를 검증했다고 간주하면 안 된다.

이전 좌석 영역 누락을 일으킬 수 있는 저장 경쟁은 재현했지만, 사용자의 과거 실행에서 바로 그 경쟁이 발생했다고 확정하지는 않는다. 루트 `AGENTS.md`, 기존 앱·ZIP, 터미널 권한은 변경하지 않았다.

## 다음 실기 확인 범위

새 패키지를 만들 때에는 앱 자신의 키보드 수신 검사, 첫 문자에서 기준색만 저장되는지, 캡챠가 닫힌 뒤 구역·좌석으로 이어지는지, 빈 좌석 화면에서 탐색이 유지되는지, 준비 중 F4·중지 버튼이 늦은 입력을 막는지를 같은 설치 앱에서 확인해야 한다. Windows는 별도의 실제 빌드·실행 검증이 필요하다.
