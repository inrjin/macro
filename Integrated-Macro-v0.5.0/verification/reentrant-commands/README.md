# 실행 명령 재시도와 수동 진입 검토

사용자는 F9·F5·F2를 다시 눌러도 기존 실행 때문에 거절되거나 무시되어 F4부터 다시 해야 한다고 보고했습니다.
추가로 캡챠를 직접 끝낸 뒤 `캡챠 이후 진행(F9): 일반 예매의 캡챠 대기 중에만 사용할 수 있습니다.`가 표시됐습니다.
[사용자 보고](user-reported-f9.json)의 실제 실행 모드·단계는 확인하지 않았으며, 아래 재현은 실제 소스와 로컬 테스트에 근거합니다.

## 변경한 동작

- F1·F2·F5 및 앱의 시작 버튼은 실행 중·이전 시작 응답 대기 중에도 새 실행을 받습니다. 새 명령이 이전 미전달 입력과 준비 요청을 취소합니다.
- F9는 수동 진입·캡챠 이후뿐 아니라 구역·좌석·실패 복구·완료 뒤에도 현재 화면을 다시 관측해 재시도합니다. F2·F5에서 F9로 전환할 수도 있습니다.
- F9는 최초 입장·날짜·회차·다음 버튼을 재생하지 않습니다. 최초 예약 버튼 전달 후 프로그램이 Entry/AwaitingMap에 남아 있어도 수동 완료 신호를 받습니다.
  예약 시각 대기·최초 버튼 전달 전·Idle·Stopped는 이 신호로 건너뛰지 않습니다.
- 같은 연결 창·크기·좌석 설정의 재시도는 전달된 좌석, 중복 클릭 차단 외곽, 실패 이력과 필요한 수량 관측 상태를 유지합니다.
  현재 좌석 설정과 이력이 호환되지 않으면 이유를 표시하며, 실제 선택을 자동으로 해제하지 않습니다.
- 완료 후 명시적 새 명령은 새 관측 뒤 완료를 다시 시도할 수 있습니다. 자동 Tick·옛 ACK만으로 완료를 반복하지 않습니다.
- **날짜·회차·예매 버튼 직접 진행**은 기본 OFF입니다. ON이면 최초 예약 클릭은 유지하고 후속 등록 좌표를 건너뜁니다.
  좌표를 삭제하지 않으며 NOL 판단·Enter 또는 F9로 진행합니다. 두 자동 캡챠 옵션이 OFF면 F9를 기다립니다.

F1은 새로운 입장 실행입니다. 구역 화면에서 다시 고르려면 F9, 이미 구역 안의 좌석 화면이면 F5를 사용합니다.
저장·좌표 지정·연결 변경은 별도의 작업 잠금을 유지합니다.

## 실제 발견하고 교정한 경계

기존 활성 실행 검사, Captcha 전용 F9 검사, UI commandBusy가 실행 명령을 거절했습니다.
요청 수신 단계의 취소 세대와 지연 응답 검사, 새 명령 소유권을 분리해 교정했습니다.

독립 검토에서 다음 추가 문제를 소스·재현으로 확인하고 수정했습니다.

- 지연된 이전 상태·오류·finally·시작 창 표시가 새 실행을 덮는 경계. 별도 상태 표시창의 지연 bootstrap 오류도 포함합니다.
- 첫 시작이 설정을 저장한 뒤 응답이 늦으면 다음 동일 설정 시작이 오래된 revision 때문에 거절되는 경계.
  동일 payload만 멱등 처리하고 다른 오래된 설정은 충돌 검사를 유지합니다.
- F9가 실패한 시작 이전의 Engine을 복원하면서 저장된 다른 색상·범위·객체 설정을 혼용하는 경계.
- 취소표 전용 영역을 유지해 F9로 전환한 뒤 F2로 돌아갈 때 동일 영역을 다른 설정으로 오판하는 경계.
- 유지한 좌석보다 목표 매수를 낮추면 추가 좌석을 누를 수 있던 경계. 현재 선택 해제·추가 클릭·완료·갱신을 보류하고 목표 증가 후 재시도를 허용합니다.
- 기존 Entry 상태를 승인한 뒤 새 캡챠 옵션으로 두 번째 검사하면서 F9를 성공 반환만 하고 무시하던 경계.

[구현 기록](implementation/README.md), [독립 Engine·호출부 검토](independent/review.md),
[반대 검토와 UI 재현](adversarial/README.md)에 반박·교정·증거를 구분했습니다.
초기 Completed 영구 no-op 검사는 폐기한 중간 정책의 기록이며 최종 동작의 근거가 아닙니다.
소스에서 찾고 교정 후 검사한 일부 경계에는 교정 전 실패 로그가 없습니다.

## 남은 검증 범위

배포 빌드, 앱 실행, 실제 OS 입력·브라우저 초점·사이트 전환과 Windows 실행은 하지 않았습니다.
검사는 실제 Engine·공유 helper·UI 처리기를 실행했으며 Worker 전체와 실제 NativeAdapter의 현장 동작을 대체하지 않습니다.

이미 OS에 전달한 입력을 되돌릴 수는 없습니다. 수량 확인 OFF의 좌석 기록은 서버 선점 확정이 아닌 기존 전달 추정입니다.
수량이 불명확하면 기존 판독 정책에 따라 대기가 지속될 수 있습니다. 새 화면·다른 공연에서도 기존 기록이 맞다는 보장은 없습니다.
macOS 물리 키 반복은 미검증이며 임의 시간 debounce를 추가하지 않았습니다. Windows 플러그인의 기존 MOD_NOREPEAT는 유지했습니다.

**현재 배포된 0.5.10 앱에는 이 수정이 반영되지 않았습니다.** 기능 소스와 검증만 완료했으며 기존 배포물과 사용자 설정은 변경하지 않았습니다.
