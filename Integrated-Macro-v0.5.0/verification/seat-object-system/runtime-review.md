# Runtime and UI review and corrections

Initial reviewer and runtime-guard implementer: `seat_shortcut`. Independent code/state review: `fix_cancellation_start`; adversarial/fixture review: `input_adversarial_review`; parent performed additional caller review. The initial review compared `before/` with runtime/UI changes. Later guard/cache changes below were implemented here and independently reviewed. No physical input, application launch, distribution build, permission change, or personal profile access occurred.

## Findings and final corrections

1. **Static SCK time used as a read ID.** A count increment before the click delay can be followed only by a valid unchanged native frame. Reusing its timestamp rejects every later count event as a duplicate. Runtime now assigns a read serial after each successful native poll and receipt/request validation. It preserves the actual native timestamps. The real-Engine negative control stalls; the serial-based positive case progresses after the delay.
2. **Count read and input used different screens.** A T0 count of one could authorize a second seat while the pre-click T1 frame already displayed two. Each input authorized by a count event now receives its own proof containing run/action/request/read IDs, geometry, detected evidence rectangle, local RGBA fingerprint and whole-frame fingerprint. A changed crop or geometry cancels the unsent action and requests another observation. Missing proof never authorizes input.
3. **A local crop omitted global contradictory evidence.** New empty text or a second heading outside an unchanged numeric crop makes the actual reader return Unreadable. `reader-review/evidence-counterexample/result.jsonl` preserves the failing crop-only model. If the whole-frame fingerprint changed, the guard now runs the full reader exactly once on the latest acquired frame and requires the same count/heading/evidence. Unknown or changed evidence cancels input. Timer-only changes pass this re-read; there is no recapture/re-read loop chasing animations. Reader opacity rejection also protects an unobserved pixel outside the local crop.
4. **Refresh/navigation could bypass the same check.** Parent identified that an old zero count could allow a refresh or legacy region movement after another selection appeared. The same proof and fresh pre-input capture now cover Refresh and `legacy_cancellation_region` Click/Key as well as Seat/Complete. Entry/CAPTCHA/Esc and the count-option-OFF path remain outside this new gate. Cancelled navigation rolls back through the existing Engine event; a late ACK does not revive it.
5. **Repeated static OCR cost.** One process-local cache stores only the pure `CountRead` result, keyed by full RGBA fingerprint and width/height/stride. Native freshness, current request, new read serial, and per-action proof still run on every valid poll. Cached Unknown stays Unknown. No action permission is cached; Start/Stop clear the cache. A changed pixel/layout triggers a new reader invocation. The hash computed for the current lookup is reused for that observation's proof.
6. **Object diagnostics used invalid component arithmetic.** One bridged color component can produce two object proposals. UI now reports color components and round-object candidates separately, including unsupported/ambiguous reasons. It no longer claims two of one component passed size rules. The option remains explicitly round-only, default OFF. Count verification is independent of the round-object option; count tests exercise the original non-object path.

7. **Count-verified legacy flows advertised ignored manual commands.** Independent helper/Engine reproduction found that a generic failure after A delivery could error, or target queued B and be ignored. A dedicated Snapshot count-verification flag now routes only manual seat failure/context recovery through delivered-attempt history, blocks unused manual selection and selected-color observation, and hides those controls. Entry/CAPTCHA/region/refresh confirmations retain their original policy. The real-Engine regression requires A attribution, rejects queued B, emits one Esc, ignores late B ACK, and distinguishes automatic foreground recovery from deliberate Pause. UI uses matching optional failure/dialog guidance without claiming attempted clicks are the site count. `visualDialogView` now displays the actual enabled count-verified monitor while still yielding to capture/pause/recovery state.

8. **The real recovery callers still used only continuous mode.** Final adversarial caller tracing found that the new count-verified manual recovery helper was unreachable for legacy runs: target recovery was not created, and native pre-delivery validation errors faulted. A shared predicate is now used at exactly those two callers. It preserves the original continuous behavior and additionally permits recovery only for count-verified Seats/Conflict/Completing. Entry/CAPTCHA/Region/WaitingRefresh and navigation freshness/yield policies are unchanged. The production predicate plus actual Engine test covers undelivered cancellation, context loss, recovery classification, Resume requiring new count/map evidence, and excluded-phase/OFF controls. This remains a helper/Engine regression, not a real Worker/native validation experiment.

## Execution and lifecycle review

- Only an accepted count event temporarily enables count-gated Engine input; later CandidatesObserved/Tick cannot manufacture a proof. Runtime attaches proof only to that event's current pending action.
- Pending-action changes, cancellation, Pause/ContextLost, Start/Stop and run mismatch invalidate proof. A cancelled action is not acknowledged as delivered. Proof reissue waits for a new request/observation.
- Seat validation uses its newest candidate frame. Every protected non-seat action also obtains a fresh validated capture. Visual-dialog checks still precede delivery. After possibly expensive re-reading, interrupt/epoch checks and the native guarded-input checks remain.
- Reader requests continue in manual Completing; Unknown never means zero or successful completion. A queued completion suppresses redundant requests, while cancelled completion returns to observation.
- The reader cache contains neither native freshness nor selection success. Origin/scale do not change pixel OCR, but current geometry is checked and recorded in every new proof.
- Paused feature changes are rejected by the existing save contract; calibration updates remain allowed.

## Cost and remaining boundaries

For a synthetic 3024×1608 RGBA frame, the debug unit benchmark measured roughly 46 ms each for full proof creation and unchanged guard. This is **not release/UI latency**. A standalone `rustc -O` benchmark of the exact production whole-frame digest function averaged **3.345 ms over 200 iterations** (`runtime-proof-hash-optimized.json`). It excludes crop work, OCR, capture, native validation and UI. The bounded cache stores only a count result and small metadata; it does not duplicate whole screenshots. Fingerprints are 64-bit process-local change detectors, not cryptographic proof.

The guard validates the latest acquired frame; the page can still change while recognition/native validation/OS delivery is in progress. It does not establish an atomic site transaction or server ownership. Supported text/layout recognition and strict opaque-frame requirements are separate reader limitations. Non-round object shapes remain unsupported by the optional round extractor, while the existing color path stays available. Windows behavior and live browser input have not been exercised here.
