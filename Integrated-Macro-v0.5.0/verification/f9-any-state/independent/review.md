## Contract and direct verification

F9 is an explicit user assertion that entry/CAPTCHA work can be left behind. It no longer requires a prior Engine phase or mode. The actual Engine matrix reaches all 14 phases through public events, then checks region priority ON/OFF, cancellation of pending input, monotonic generation/action IDs, old ACK rejection, and no revival of scheduled/registered entry. Additional tests cover all three modes, Stop followed by F9, a newer Stop defeating subsequent input, direct event use, option combinations, retained legacy footprints, and count request/receipt lineage.

This is not automatic classification of every real browser screen. F9 retains physical target/permission/capture checks and compatible retained ROI/color/count/object settings. Recoverable foreground/occlusion loss waits for the bound target. Missing permission, calibration changes or incompatible retained settings still cannot safely produce a click. An already posted native input cannot be recalled.

## Findings, corrections and objections

1. **Former phase restrictions rejected explicit F9.** `before.log` records five tests failing against the earlier gate, including Idle, Stopped and undelivered entry. Engine `can_manually_complete_captcha` now accepts explicit override; `restart_post_entry` cancels pending work, clears the entry queue, confirms the handoff and requires new map/count evidence. Enter/CAPTCHA automation retains its separate gate.
2. **Failed Escape lost its known dialog on F9.** `escape-before.log` reproduces Seat ACK → confirmed conflict → failed Escape ACK → Faulted → F9 yielding Seats, not Conflict. The visual incident could remain active while the runtime rearm path required Conflict. A failed Escape now clears only its delivery latch, and `fault` preserves the preceding phase for explicit conflict retry. The final test confirms one new Escape, no replay of an acknowledged Escape, and useful next-seat progress after a separate closed-dialog observation.
3. **A legacy known failure became a retained attempt.** `legacy-conflict-before.log` reproduces the confirmed-result route: Seat ACK → SeatResult Conflict → Escape ACK → F9 → dialog closed, leaving failed A in attempted count. The failure is now removed from selected/attempted and recorded as rejected when first observed. Final direct and Stop-mediated branches preserve that exclusion. The legacy current identity remains available while conflict recovery is active.
4. **Legacy conflict retry was routed to a nonexistent optimistic receipt.** After F9 enables continuous search, a legacy SeatResult retry formerly would enter the optimistic path even though legacy delivery has no `DeliveredSeatAttempt`. The final source uses a narrow current-known-legacy-conflict exception and a shared runtime `known_conflict_retry_event`. The independent queued/failed/delivered Escape matrix verifies the first two can retry once and successful delivery remains latched. It does not fabricate a delivery action ID.
5. **Epoch ownership, binding provenance and capture commits were reviewed at callers.** F9 ownership now uses the current control epoch, not its receive timestamp relative to Worker initialization. A later F4/F1/F2/F5 invalidates older work. Bind changes compare window ID and PID and reset previous-window Engine/receipt/proof state. F9 commits the post-entry checkpoint before native validation, so recoverable context loss cannot resume the old entry queue. F8 rechecks the capture epoch after publish/log work and before saving its local profile clone; stale replies also are not published as a successful capture.
6. **F4 discarded an already known unresolved dialog.** Stop now first cancels unposted actions, then checkpoints a known conflict, then stops input. This order makes a queued Escape eligible for later retry while preserving the successful-Escape latch. Repeated Stop keeps that checkpoint; an ordinary speculative watch is discarded. F9 restores the same-context checkpoint through the existing runtime path. Actual shared helpers, Engine and VisualRecovery are tested for visual/legacy routes crossed with queued/failed/delivered Escape; separately, a dialog already closed while stopped restores before a needless Escape. F1's actual new run and a successful different-window binding retain their existing resets.
7. **Successful same-window Bind resets native frame sequence numbers.** Preserving an incident without accounting for the capture stream reset would ignore new frames numbered below the old sequence. The final `same_target_stream_restarted` resets only current-stream ordering. Comparisons use a local baseline copy with sequence zero while preserving original baseline pixels and reported provenance. The test checks old sequence 100/101 followed by new 1/2; raw native/count frame metadata are unchanged. Caller review confirms this method is invoked only after successful same-ID/PID binding. Duplicate current-stream frames remain rejected.

The implementation and adversarial reviewers exchanged objections for the Faulted Escape, legacy Stop lifetime, missing legacy receipt, binding provenance and timestamp cases. Their corrections were read in actual production methods and callers. Peer `../implementation/desktop-final.log` reports 129 runtime/helper tests passed and one manual timing test ignored; this reviewer did not claim whole-Worker or OS execution from those helper tests.

## Preserved behavior and limits

- Retained/actually delivered footprints survive an explicit same-context restart, including F4 followed by F9; queued unsent seats do not become retained. Known failures remain excluded according to the existing retry policy. Different bound windows discard previous-window selection history.
- Explicit completion retries require a new candidate generation with count OFF, or a new accepted count request with count ON; Tick, old ACK and stale count events do not authorize completion. The prior 15 tests also cover target reduction/raising, mode transitions, zone ROI/color/completion, and manual-entry ON/OFF.
- Tests inject delivery and count/failure observations separately. They do not prove server reservation, popup attribution, OCR success, current-page semantics or actual mouse/key delivery. A same-sized window may show a different semantic performance; new-window discovery remains outside this change.
- A manually confirmed legacy conflict has no image incident to prove closure; its existing explicit closure confirmation remains distinct from automatic visual restoration. F9 does not solve every unidentified dialog.
- A failed target lookup/validation preserves the existing binding context. A native driver bind failure can clear `NativeAdapter.target`; a subsequent successful reconnect is conservatively treated as a new context and discards the old checkpoint. Preserving history through every native binding failure is not guaranteed and was explicitly accepted as outside this correction. No actual driver-failure injection was executed.
- Historical `verification/reentrant-commands/independent/` logs and notes were preserved. Their earlier F9 phase restrictions and F4-history descriptions are superseded by this user-authorized policy, not re-labelled as current results.
- No app launch, live site operation, permission change, Windows runtime test, user profile write or distribution build was performed by this reviewer. The parent owns the separately authorized 0.5.11 build and final artifact verification.

The post-checkpoint Stop/conflict correction and capture-stream boundary have been read in the final source and affected callers. No remaining blocking defect was found within the stated scope. Release build results are separate and are not implied by this component review.
